# LLM 辅助建模能力评估(基于本实验)

> 依据本实验的 [results.md](results.md) / [transcript.md](transcript.md) / [session-log.md](session-log.md)。
> **前提(决定结论的适用范围)**:**n=1** —— 单一模型(Bank Office,**教科书型 DES**,M/G/1 甜区)、单一 LLM(**Claude Opus 4.7,带官方文档上下文**)、AnyLogic 8.9.8 **PLE**。下表"已验证"仅指**在此设定下被实际跑通/打分**,不等于普遍结论;每项附信心评级。

## 一、本实验验证了的能力

### A. 设计端 —— Tier A(LLM 出方案,人在 GUI 搭)

| 能力 | 证据 | 评级 |
|---|---|---|
| 从自然语言推出**模型结构**(块 + 拓扑) | Phase 1/3/4 与官方解法 **100% 一致** | ✅ 强 |
| **块类型选择**(ATM=Delay 非 Service;柜员=Service+ResourcePool) | Phase 1/3 赌中(且事先自标为不确定点) | ✅ 强 |
| **API/表达式召回**(`triangular`、`tellers.utilization()`、`ATM.statsUtilization.mean()`) | 三阶段**零幻觉**;连自标"最不确定"的 `statsUtilization.mean()` 也对 | ✅ 强 |
| 判断**该不该写自定义 Java** | 正确预测 Phase 1/3/4 仅需内置表达式、无需自定义代码 | ✅ 中-强 |
| **定量推理**(利用率量级) | 预测 ATM 0.38(实测 **0.38**)、柜员 ~0.49(实测 **0.47**) | ✅ 中-强 |
| 具体**参数取值** | "形对值偏":分布族/单位/模式对,数值与官方不同 | ◐ 中(无可厚非——问题描述未给数值) |

### B. 模型文件端 —— Tier C(人搭框架,LLM 改 XML)

| 能力 | 证据 | 评级 |
|---|---|---|
| **读多部件 ALPX**、据其核对产出 | 全程靠 XML 复核块/参数/接线(还借此打分) | ✅ 强 |
| 经 XML **编辑元数据**(7 块 description) | 重载 7/7 显示、well-formed、零返工 | ✅ 强(配 diff 法) |
| 经 XML **给既有块注入会编译的 Java 行为** | `sink.onEnter` 的 `traceln` 编译通过 + 运行输出 | ✅ 中(配 diff 法;门槛=能编译,比"能打开"高) |

**共同护城河(已验证有效)**:**先取一份 AnyLogic 自己写出的真样本,再仿其序列化**(diff 法)——description 与 code-value 的格式都不是猜的。

### C. 同样被验证的"局限 / 风险"(也是结论)

- **参数数值不可当真**:LLM 给的是合理占位,需建模者按真实数据定。
- **UI 位置 / 默认行为的臆断不可靠**:Phase 3「SelectOutput 默认=condition-true」、Phase 4「统计在 Statistics 区 / 需手动开」两次都栽于此——**只有实跑 / 查文档 / 取样能定**。
- **LLM 当"核查者"也会凭空造 bug**:Phase 3 据 XML 臆断、报了个**不存在的"静默 bug"**,被实跑推翻。→ 风险**不只在生成端,也在审查端**。
- **一句话画像**:**对"是什么"(块 / 方法 / 结构)可靠;对"在哪点 / 默认怎样 / 数值多少"不可靠。**

## 二、还可继续验证的能力 / 场景

按「信息量 × 当前可行性」排序。

### 高优先(PLE 可行,直接接续本实验)

1. **新建全新元素类型**(Function / Variable):Tier-C 梯度的下一格——从"填既有字段"到"**造新元素**"。用 diff 法逼近。**本会话明确还没碰。**
2. **强制需要真 Java 的动态逻辑**:复杂 SelectOutput 条件、自定义路由、非平凡 Function、statechart。Phase 1/3/4 几乎不需代码,**没真正压到"写逻辑 + 调错"**。
3. **调试闭环**:本实验近乎零报错。造一个会编译/运行报错的场景,测"红字回喂 → LLM 修"的成功率与轮数(L1 工作流核心)。
4. **非教科书模型**:Bank Office 是 M/G/1 甜区。换一个**网上少见**的系统,测 LLM 离开记忆模式后的真实水平(L1/L3/landscape 预测的边界)。

### 中优先(换范式 / 换轴)

5. **换建模方法**:System Dynamics(如 Bass 扩散,L1 已知参数基线)、Agent-Based(statechart)——不同范式、不同能力画像。
6. **抽象层次 / 方法选择**(L3 的"艺术"):给含糊问题,看 LLM 选 SD vs DES vs ABM、定抽象层次是否与专家一致——最依赖人类判断、最可能是弱点。
7. **LLM 读结果**(L5 轴):把运行输出回喂 LLM 做分析,测时序/因果归因准确度。本实验只测"产出端",没测"分析端"。
8. **从零生成流程图拓扑**(L4/L9 核心开放问题):整套 ALPX(块 + 连线 + 一致的 ID 交叉引用),测脆弱边界。

### 需额外条件 / 许可证

9. **设计期 Python API**(原始设想):用 `.venv` 里的 beta 程序化生成**空间标记**;先验证 PLE 是否有 Graphical Editor API Connector。
10. **程序化运行评测闭环**:`engine.runFast()`(需 Professional 导出)或 AnyLogic Cloud——license/Cloud 是硬成本(本会话已厘清)。
11. **跨模型 / 跨时间**:本实验只 Claude Opus 4.7。换模型 + 日后重跑,兑现 repo 用日期前缀追踪能力演化的设计。

### 方法论上可加强

12. **去污染的被测设计**:本实验 Claude 既当被测又当打分,有自评偏倚;可用 subagent(只给问题、不给官方解)当被测、另一方持 ground truth 打分。
13. **n>1 与量化**:多模型 × 多任务 × 重复,产出成功率/幻觉率**分布**,而非单例轶事。

## 三、与 landscape 报告的关系

本实验为 [landscape 报告](../../reports/llm-assisted-modeling-landscape.md)提供:

- **Tier A 的量化正例**(教科书 DES 上结构/API 几乎零摩擦);
- **一条新边界刻画**:「**结构/API 可靠,UI 流程/默认行为不可靠**」,可作为后续跨模型评测的固定维度;
- **Tier C 的首个正向数据点**:改既有 XML(元数据 + 既有字段的会编译 Java)可靠,但"生成新元素/新拓扑"仍未测。
